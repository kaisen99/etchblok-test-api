The codebase uses a consistent `to_dict` and `from_dict` pattern across its domain models to bridge the gap between Python objects and JSON-based API interactions. This pattern ensures that complex types like Enums and datetimes are handled uniformly while maintaining a clear separation between internal state and external representations.

## The `to_dict` Pattern

The `to_dict()` method is implemented on every domain model to provide a JSON-serializable dictionary representation. This is primarily used in the route layer (e.g., `app/routes/bookmarks.py`) to return responses via Flask's `jsonify()`.

### Handling Complex Types
The implementation specifically addresses types that are not natively JSON-serializable:
*   **Enums**: Converted to their underlying value using `.value`.
*   **Datetimes**: Converted to ISO 8601 strings using `.isoformat()`.
*   **Computed Properties**: Includes derived data that isn't stored as a field (e.g., the `size` of a collection).

For example, in `app/models/bookmark.py`, the `Bookmark.to_dict` method handles both status enums and timestamps:

```python
def to_dict(self) -> Dict[str, Any]:
    """Serialise to a plain dictionary for JSON responses."""
    return {
        "id": self.id,
        "url": self.url,
        "title": self.title,
        "description": self.description,
        "tags": self.tags,
        "status": self.status.value,  # Enum to string/int
        "created_at": self.created_at.isoformat(), # Datetime to string
        "updated_at": self.updated_at.isoformat(),
        "metadata": self.metadata,
    }
```

## The `from_dict` Pattern

The `from_dict()` class method serves as a factory for creating model instances from raw dictionary data, typically sourced from `request.get_json()`. 

### Asymmetric Deserialization
A critical characteristic of this codebase is that `from_dict` is **not** a full symmetric deserializer. It is designed for **creation flows** rather than restoring a full object state from a database. 

*   **User-Provided Fields**: It extracts fields that a user is allowed to provide during creation (like `url`, `title`, or `name`).
*   **Generated Fields**: It ignores fields like `id`, `created_at`, and `updated_at`. These are automatically generated by the class's `field(default_factory=...)` definitions when the instance is initialized.

In `app/models/tag.py`, the `from_dict` method also handles the conversion of incoming strings back into Enum types:

```python
@classmethod
def from_dict(cls, data: Dict[str, Any]) -> "Tag":
    """Construct a Tag from a dictionary."""
    # Convert string color back to TagColor Enum
    color = TagColor(data["color"]) if "color" in data else TagColor.GRAY
    return cls(
        name=data["name"], 
        color=color, 
        description=data.get("description", "")
    )
```

## Integration Flow

The serialization patterns facilitate a standard data flow from the API request to the persistence layer.

1.  **Route Layer**: Receives JSON and passes the dictionary to the service.
2.  **Service Layer**: Validates the data and calls `Model.from_dict(data)`.
3.  **Model**: Initializes itself, generating a unique ID and timestamps.
4.  **Repository**: Persists the resulting object.

This flow is visible in `app/services/bookmark_service.py`:

```python
def create_bookmark(self, data: Dict[str, Any]) -> Tuple[Optional[Bookmark], Optional[str]]:
    # 1. Validation
    error = _validate_url(data.get("url", "")) or _validate_title(data.get("title", ""))
    if error:
        return None, error

    # 2. Deserialization via from_dict
    bookmark = Bookmark.from_dict(data)
    
    # 3. Persistence
    self._repo.save_bookmark(bookmark)
    return bookmark, None
```

## Model Mapping Summary

Each model implements these patterns with slight variations based on their requirements:

| Model | `to_dict` Special Handling | `from_dict` Required Fields |
| :--- | :--- | :--- |
| **Bookmark** | ISO timestamps, `status.value` | `url`, `title` |
| **Tag** | `color.value` | `name` |
| **Collection** | Computed `size` property, `type.value` | `name` |

### Note on Updates
While `from_dict` is used for creation, updates (PUT requests) typically do not use it. Instead, the service layer (e.g., `update_bookmark` in `app/services/bookmark_service.py`) performs partial updates by manually mapping keys from the request dictionary to the existing model instance's attributes and calling `_touch()` to refresh the `updated_at` timestamp.
